# Bind migration plans to an installed Knowledge identity

The offline migration orchestrator invokes the selected independent Knowledge interpreter's `knowledge_platform.distribution.installed_identity` CLI before planning and after the migration delegate. The strict versioned receipt contains package/version, owned-distribution digest/count and an explicit unauthenticated scope. Harness does not import Knowledge implementation. The plan binds this receipt together with executable identity; retries with changed installed code, including the same package version, reject. Older plans without these fields cannot be resumed by the new orchestrator.

The post-delegate comparison precedes final receipt/checkpoint publication. An installation changed during migration leaves an inactive intermediate checkpoint, never a completion acknowledgment. Failed completed retries preserve the old receipt commitment. Snapshot admission descriptors remain inherited by identity subprocesses as well as migration subprocesses.

The selected interpreter and first installed receipt are trusted operator inputs, not signed artifact provenance. A compromised interpreter/identity implementation can forge its own observation. This does not cover generated bytecode, dependencies or interpreter startup hooks, nor does it atomically fence package replacement during execution. The offline migration, target-freeze and writer-barrier entrypoints all bind installed identity. Freeze and suspension capture identity before the first Harness mutation and recheck around delegated Knowledge operations and completion publication. An old plan without identity or a changed same-version installation rejects; partial or completed frozen checkpoints are retained for explicit recovery, never automatically thawed. It is not a unified active-installation revision, permission reassignment, CUTOVER or thaw.
